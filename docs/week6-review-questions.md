# 6주차 Review Questions

## Intersection Observer API를 활용한 무한 스크롤의 구현 방식과 고려한 사항

기존 홈 피드는 본인 게시물을 제외하고 날짜 내림차순으로 정렬한 목록 전체를 한 번에 출력했습니다. 이를 서버에서 첫 페이지를 만들고, 클라이언트에서 다음 페이지를 추가하는 구조로 개선했습니다.

1. 서버 컴포넌트에서 순수 함수 `getFeedPage()`로 첫 게시물 3개와 다음 위치를 계산해 클라이언트 목록에 전달합니다. 첫 화면의 게시물은 서버가 만든 HTML에 포함됩니다.
2. 클라이언트 목록 하단의 감지 요소를 `IntersectionObserver`로 관찰합니다. `rootMargin`을 `300px 0px`로 두어 감지 요소가 화면 근처에 오고 다음 페이지가 있으면 추가 로딩을 시작합니다.
3. `fetchFeedPage()`는 기존 목데이터를 페이지당 3개씩 나누어 반환합니다. 추가 로딩에는 약 400ms의 지연을 두어 비동기 요청을 모사합니다. 현재 홈 피드 데이터에서는 화면에 보이는 게시물이 3개 → 6개 → 8개로 늘어납니다.
4. 반환값은 `{ items, nextCursor }`입니다. 로딩이 끝나면 기존 게시물 뒤에 결과를 추가하고 다음 위치를 갱신합니다. 현재 데이터의 다음 커서는 `3` → `6` → `null`입니다. 추가 페이지 유무는 `nextCursor !== null`로 판단하며 마지막 페이지에서 요청을 중단합니다.

중복 로딩을 막기 위해 진행 중인 요청을 `ref`로 보관합니다. 감지 콜백이 여러 번 실행돼도 상태 렌더링을 기다리지 않고 같은 페이지의 동시 요청을 차단합니다. 게시물에는 기존 ID를 그대로 사용해 좋아요·댓글·저장 상태와 연결을 유지합니다.

컴포넌트를 정리할 때는 Observer 연결을 해제하고 `AbortSignal`로 대기 중인 목 요청을 취소합니다. 추가 로딩 중에는 이미 표시한 게시물을 유지하고 목록 아래에 `FeedPostSkeleton`을 표시합니다. 각 카드의 첫 이미지 로딩 중에도 기존 Skeleton 표시를 유지합니다. 요청 오류에는 재시도를 제공하고, 키보드 사용자와 Observer를 사용할 수 없는 환경을 위해 더 불러오기 버튼도 둡니다.

외부 API 없이 기존 목데이터를 사용하므로 실제 서버의 페이지 조회나 캐싱은 구현 범위에 포함하지 않았습니다. 목록 분할과 관찰 상태 관리에 집중했으며, UI에서 3개 → 6개 → 8개 추가와 마지막 페이지 안내를 확인했습니다.

## 5주차에서 6주차로 발전시키며 중점적으로 고려한 사항과 이유

5주차에 구현한 화면, 동적 경로와 게시물 상호작용을 유지하면서 사용자가 체감할 수 있는 개선을 추가하는 데 집중했습니다. 진우는 이미지 Skeleton, 더블탭 좋아요와 하트 효과, 내 게시물별 좋아요 수 숨김을 구현했습니다. 규민은 홈 피드 무한 스크롤과 내 소개글 편집을 구현했습니다. 다섯 가지 개선 기능은 PR #9–13을 통해 `submit/week6`에 병합했습니다.

서버·클라이언트 컴포넌트의 경계도 유지했습니다. 첫 목록 계산과 정적인 페이지 구조는 서버에 두고 화면 관찰·추가 로딩·편집 입력을 클라이언트 컴포넌트로 분리했습니다. 프로필 편집은 실제 Instagram 화면을 참고해 `/accounts/edit`라는 별도 설정 페이지로 구성했습니다. 서버에서 현재 사용자 정보를 선택하고, 폼은 소개글 제출·취소와 150자 제한을 처리합니다.

소개글은 `useProfileBio` 훅에서 `localStorage`와 연결했습니다. 서버에서 브라우저 저장소를 읽지 않도록 서버 snapshot을 분리하고, 저장이 끝나면 구독 중인 프로필에도 변경을 반영합니다. 줄바꿈이 있는 소개글의 저장·새로고침 유지, 취소, 빈 내용 저장과 길이 제한을 UI에서 확인했습니다.

기존 게시물 ID와 데이터 구조를 유지해 프로필·상세 화면의 상태 연결을 보존하고, Skeleton을 재사용해 이미지와 목록 로딩의 표현을 맞췄습니다. 외부 API나 새 상태 관리 라이브러리를 추가하기보다 필수 요구사항과 합의한 기능을 완성하는 것을 우선했습니다.

이번 미션을 하나의 Sprint로 정리해 README에 목표, 담당자, Backlog와 기술 회고를 기록했습니다. 기능 구현·PR 병합, UI 확인과 통합 커밋의 Vercel 빌드가 끝난 항목을 기록하고, 공개 배포 주소에 최신 코드를 반영하는 작업과 최종 제출을 남은 단계로 구분했습니다.
